# 11차 (2부): 공고 마감 배치

2026-10-26, 브랜치 `feature/sprint11-egov-batch`

매일 자정에 공고 접수를 마감하던 UPDATE 한 번을 eGov 배치 잡으로 바꿨다. 이제 실행할 때마다 기준일, 결과, 건수가 남고, 총괄관리자는 시스템 관리 > 배치 실행 이력에서 기록을 보거나 바로 실행할 수 있다.

![배치 실행 이력 화면](images/batch-history.png)

## 왜 바꿨나

전에는 마감 결과가 "n건 전환" 로그 한 줄뿐이라, 언제 어떤 날짜 기준으로 돌았는지 화면에서 볼 수 없었다. 공고가 적어서 속도만 보면 UPDATE 한 번이 낫지만, 공공 SI 에서는 배치를 eGov 배치 실행환경으로 만드는 경우가 많아 직접 써 보고 싶었다. 청크마다 커밋하니 대상이 많아져도 트랜잭션 하나가 커지지 않는다.

## 구조

- 스케줄러가 매일 자정과 서버 기동 직후에 잡을 실행하고, 기준일(`targetDate`)을 파라미터로 넘긴다.
- 잡은 스텝 하나다. 마감 대상을 100건씩 읽고(MyBatis 페이징 리더) 한 번에 마감한다(배치 라이터).
- 실행 기록은 Spring Batch 메타데이터 테이블에 남는다. 테이블은 Flyway V7 로 만들었다.

## 신경 쓴 부분

### 같은 날짜는 한 번만

Spring Batch 는 잡 이름과 식별 파라미터가 같으면 같은 실행으로 본다. 기준일을 식별 파라미터로 두었기 때문에, 이미 성공한 날짜로 다시 돌리면 예외가 나고 스케줄러는 "이미 처리한 날"로 보고 넘어간다. 그래서 자정에 돈 뒤 서버를 다시 띄워도 다시 마감하지 않는다.

관리자가 누르는 "지금 실행"은 요청 시각을 파라미터에 더해서 새 실행이 되게 했다.

### 페이징 리더와 OFFSET

페이징 리더는 다음 쪽을 OFFSET 으로 읽는다. 그런데 이 잡은 읽은 공고를 마감 상태로 바꾸기 때문에, 첫 청크가 커밋되면 남은 공고가 앞으로 당겨진다. 250건이면 둘째 쪽을 OFFSET 100 으로 읽는 순간 100건을 건너뛰고, 결국 150건만 마감하고 끝난다.

그래서 SQL 에서 OFFSET 을 빼고 늘 첫 쪽만 읽게 했다. 쪽 크기는 청크 크기와 같다. 테스트에서 250건을 넣고 커밋 3번(100, 100, 50)에 모두 마감되는 것을 확인한다.

### 트랜잭션 안에서 잡을 시작하면 안 된다

JobRepository 는 이미 열린 트랜잭션 안에서 잡을 시작하면 거부한다. 서비스 메서드에는 eGov 트랜잭션 AOP 가 걸려 있어서, "지금 실행"은 서비스를 거치지 않고 컨트롤러가 스케줄러를 바로 부르게 했다.

### 메타데이터 테이블은 Flyway 로

이 프로젝트는 스키마를 Flyway 로만 바꾸기 때문에 Spring Batch 의 자동 생성(`initialize-schema`)은 껐다. 서버가 뜰 때 등록된 잡을 모두 실행하는 기능(`spring.batch.job.enabled`)도 껐다. 언제 돌릴지는 스케줄러가 정한다.

## 확인

- 테스트 246건 통과. 배치 테스트 4건: 250건 마감, 같은 날짜 1회만, 지금 실행과 이력, 담당자 접근 차단
- 실제로 띄워서 기동 직후 실행, 같은 날 재기동하면 건너뜀, 지금 실행이 이력에 쌓이는 것까지 확인

- 서버를 여러 대 둘 때 한 대에서만 돌게 하기 (지금도 같은 날짜는 한 번만 성공하지만 실패 로그가 쌓인다)
