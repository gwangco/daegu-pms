# 10차 스프린트 — 신청서 임시저장·제출 취소

작업일: 2026-10-23 · 브랜치: `feature/sprint10-application-draft` · 이전 문서: [9차 스프린트](SPRINT9_COMPANY_SIGNUP.md)

## 한눈에 보기

- 사업계획서를 한 번에 다 쓰지 않아도 된다. 과제명만 적고 **임시저장**한 뒤, 접수 기간 안에 이어서 작성해 제출한다.
- 제출한 뒤에도 **서류 검토가 시작되기 전이고 접수 기간 안이면 제출을 취소**하고 고쳐서 다시 낼 수 있다. 접수번호는 처음 받은 번호 그대로다.
- 임시저장은 제출 전이라 **신청한 기업만** 본다. 담당자 목록·상세·통계 어디에도 나오지 않는다.
- "제출된 신청서는 필수 항목이 모두 있어야 한다"는 규칙을 DB **CHECK 제약**으로도 지킨다.

![임시저장 작성 화면과 제출 취소한 신청서](images/application-draft.png)

왼쪽은 과제명만 적고 임시저장한 뒤 이어서 작성하는 화면이다(버튼 두 개: 임시저장 / 사업계획서 제출). 오른쪽은 제출한 신청서를 서류 검토 전에 취소한 모습이다. 접수번호는 그대로이고 상태는 임시저장으로 돌아갔다.

## 1. 범위

상태 코드에 `TEMP_SAVED`(임시저장)가 있었지만 쓰는 곳이 없었다. 이번에 기업 쪽 신청 흐름을 "작성 → 임시저장 → 제출 → (검토 전) 제출 취소 → 다시 제출"로 넓혔다. 담당자의 심사 흐름은 바꾸지 않았다.

## 2. 바뀐 것

| 영역 | 이번 | 검증 |
| :--- | :--- | :--- |
| 임시저장 | 작성 화면 "임시저장" 버튼. 과제명만 있으면 저장, 접수번호·제출 일시 없음 | `draftNeedsOnlyProjectName` |
| 이어서 작성·제출 | `/applications/{번호}/edit`. 제출할 때 필수 항목·금액·사업계획서 확인, 접수번호 발급 | `continueAndSubmit` |
| 제출 취소 | 접수완료 + 접수 기간 안 + 본인만. 임시저장으로 되돌리고 접수번호 유지 | `withdrawAndResubmitKeepsReceiptNo`, `withdrawRules` |
| 삭제 | 본인 임시저장만. 저장한 사업계획서도 지움 | `deleteDraftOnly` |
| 공개 범위 | 담당자·평가위원·다른 기업에게 임시저장은 404, 목록·상태 검색·통계에서 제외 | `draftIsPrivateToOwner` |
| 한 공고 하나 | 신청 화면을 다시 열면 임시저장은 이어서 작성으로, 제출한 공고는 상세로 | `oneApplicationPerAnnouncement` |
| DB 제약 | V5: 임시저장을 위해 NOT NULL 을 풀고 CHECK 로 제출 건의 필수 항목 보장 | `checkConstraintRejectsIncompleteSubmission` |
| 상태머신 | 담당자 선택지에 임시저장 없음, 제출 취소는 접수완료만 | `ApplicationStatusTest.draftAndWithdraw` |
| 화면 | 상세에 "이어서 작성·삭제"와 "제출 취소" 안내, 메인 처리할 일 "작성 중인 신청서" | 헤드리스 Chrome |

테스트 224건 → 233건.

## 3. 상태 흐름

```text
 (기업) 작성 ──임시저장──▶ TEMP_SAVED ──제출──▶ SUBMITTED ──서류검토(담당자)──▶ DOCUMENT_PASSED ─▶ …
                              ▲  │                │
                              │  └─삭제            │
                              └──제출 취소(기업, 서류 검토 전·접수 기간 안)──┘
```

- 임시저장 → 제출은 기업만 한다. 담당자의 "심사 상태 변경"에는 임시저장이 나오지 않는다.
- 처음 제출할 때 접수번호(eGov ID Generation)를 받는다. 제출 취소 후 다시 내면 같은 번호를 쓴다.

## 4. 정한 것

**① 임시저장은 과제명만 필수.** 작성 중인 내용을 잃지 않는 게 목적이라 요구 조건을 최소로 했다. 다만 적은 값은 길이·금액 범위를 지켜야 저장된다. 필수 항목·금액 한도·사업계획서는 제출할 때 확인한다.

**② 버튼 두 개, 처리기 두 개.** "임시저장" 버튼에 `name="draft"` 를 주고, 컨트롤러는 `@PostMapping(params = "draft")` / `params = "!draft"` 로 나눴다. 임시저장 처리기는 Bean Validation(`@Valid`)을 하지 않고, 제출 처리기만 한다. 화면에서는 `formnovalidate` 로 브라우저의 필수 입력 검사도 건너뛴다.

**③ 중복 제출 방지 스크립트와의 충돌.** 공통 스크립트가 제출 순간 모든 버튼을 비활성화하는데, 비활성화된 버튼의 값은 전송되지 않는다. 그대로 두면 "임시저장"을 눌러도 제출로 처리된다. 그래서 누른 버튼(`event.submitter`)의 이름·값을 숨은 칸으로 옮긴 뒤 비활성화하고, 뒤로 가기로 돌아온 화면에서는 그 숨은 칸을 지운다.

**④ 임시저장은 본인만.** 목록은 서비스가 권한에 따라 `excludeDraft` 를 덮어써서 담당자·평가위원에게서 뺀다. 상세는 접근 검사기가 임시저장이면 본인이 아닐 때 404 로 답한다(있는지도 알리지 않음). 메인 통계의 "총 신청"도 임시저장을 세지 않는다.

**⑤ 잠그고 확인한다.** 이어서 작성·제출·제출 취소·삭제는 모두 신청서 행을 `SELECT … FOR UPDATE` 로 잠근 뒤 본인 여부와 상태를 확인한다. 공고도 화면이 보낸 번호가 아니라 잠근 행의 공고로 접수 기간을 본다(테스트가 마감된 공고 번호를 보내도 무시되는지 확인).

**⑥ DB 가 마지막 방어선.** 임시저장 때문에 접수번호·금액·요약·제출 일시의 NOT NULL 을 풀었다. 그 대신 CHECK 제약 `status = 'TEMP_SAVED' OR (필수 항목이 모두 있음)` 을 걸어, 서비스를 거치지 않은 UPDATE 가 빈 신청서를 접수 상태로 만들어도 DB 가 거부한다. MySQL 은 8.0.16 부터 CHECK 를 실제로 검사한다.

## 5. 트러블슈팅

| 증상 | 원인 | 해결 |
| :--- | :--- | :--- |
| CHECK 제약을 넣자 기존 테스트 5건(동시성·엑셀) 실패: `Check constraint 'ck_application_submitted_complete' is violated` | 제출 일시의 기본값(`CURRENT_TIMESTAMP`)을 없앴더니, 기본값에 기대어 접수 상태 신청서를 넣던 테스트 데이터가 제출 일시 NULL 이 됨 | 기본값은 유지하고, 임시저장 INSERT 와 제출 취소 UPDATE 에서만 NULL 을 직접 넣음. 제약이 실수를 바로 잡아낸 사례 |
| 이어서 작성 후 제출 테스트가 저장 화면만 다시 보여 줌 | 작성 폼에는 숨은 공고 번호 칸이 있는데 테스트 요청에 없어서 `@NotNull` 검증에 걸림 | 테스트를 실제 폼과 같게. 서비스는 이 값 대신 잠근 신청서의 공고를 쓴다 |
