## 1. SI 산출물

| 산출물 | 만드는 방법 | 내용 |
| :--- | :--- | :--- |
| 테이블 정의서 | `python scripts/generate-db-docs.py` | 업무 8, 공통컴포넌트 9 테이블의 컬럼·타입·NULL·기본값·키·설명, 인덱스·외래키·CHECK·생성 컬럼. 배치 메타데이터와 관리 테이블은 용도만 |
| ERD | 같은 스크립트 | 외래키는 실선, 외래키 없이 값으로 잇는 관계는 점선(Mermaid). 외래키를 두지 않은 이유 표 |
| 화면 목록·요구사항 추적표 | 직접 작성 | 화면 27개의 URL·템플릿·접근 권한·검증 테스트, 요구사항 13개를 화면·구현 위치·테스트로 연결 |

**정의서를 생성으로 만든 이유.** 손으로 쓴 테이블 정의서는 마이그레이션이 하나 늘 때마다 실제 스키마와 어긋난다. 그래서 설명은 DDL 의 COMMENT 에 두고 문서는 `information_schema` 에서 다시 만든다. 스크립트는 접속 정보를 환경변수나 `config/dpms-secret.yml` 에서 읽고, 비밀번호는 명령줄에 남기지 않는다(`MYSQL_PWD`). 분류 목록에 없는 새 테이블이 생기면 "분류 전" 절에 따로 모아 빠뜨리지 않게 했다.

**요구사항 추적표에 테스트를 붙인 이유.** SI 의 추적표는 요구사항 → 설계 → 구현 → 시험을 잇는 표다. 시험 칸을 실제 테스트 클래스로 채우면 "이 요구사항은 무엇으로 확인했나"에 바로 답할 수 있다. 테스트가 없는 요구사항은 표에 넣지 않았다.

## 2. 후속 테스트

**공지 동시 첨부 (8차 후속).** 담당자와 관리자가 같은 공지에 동시에 파일을 올리는 경우다. 앞 요청은 트랜잭션 안에서 실행하고 커밋을 미룬다. 뒤 요청은 다른 스레드에서 실행하며 게시물 행 잠금(`SELECT … FOR UPDATE`)을 기다린다. 앞 요청이 커밋하면 뒤 요청은 앞 요청이 만든 첨부 묶음을 보고 다음 순번(1)으로 붙인다. 묶음이 둘로 갈라지거나 순번이 겹치지 않는다.

- 잠금 SQL 에서 `FOR UPDATE` 를 잠시 빼고 돌리면 이 테스트가 실패하는 것을 확인했다. 잠금이 없으면 뒤 요청이 잠금 전에 읽은 예전 값(첨부 없음)으로 새 묶음을 만든다.
- 잠금이 첫 문장이라는 점도 중요하다. REPEATABLE READ 에서는 첫 일반 조회 때 읽기 기준 시점이 정해지므로, 잠금 전에 조회를 하면 잠금을 얻은 뒤에도 예전 최대 순번을 읽는다.

**동시 가입 (9차 후속).** 가입 서비스는 아이디·사업자등록번호 중복을 먼저 확인하고 저장한다. 두 가입이 동시에 들어오면 둘 다 확인을 통과할 수 있다. 테스트는 앞 가입을 커밋하지 않은 채 뒤 가입을 시작해 그 순간을 만든다. 뒤 가입은 확인을 통과한 뒤 저장에서 DB 의 기본키·UNIQUE 잠금을 기다린다. 앞 가입이 커밋하면 중복 오류가 나고, 서비스는 이를 "방금 같은 아이디나 사업자등록번호로 가입한 계정이 있습니다" 안내로 바꾼다. 같은 사업자등록번호와 같은 아이디, 두 경우를 확인한다.

두 테스트는 기존 신청서 동시성 테스트와 같은 방법을 쓴다. 고정 sleep 대신 MySQL `performance_schema.data_lock_waits` 로 실제 잠금 대기를 확인한다. 그래서 이 부분을 `DatabaseLockWait` 로 묶어 세 클래스가 같이 쓴다.

## 3. uat·sec 비교

공통컴포넌트 v5.0.7 원본을 확인해 항목별로 비교했다. 크게 다른 곳은 세 군데다. 회원 저장(유형별 테이블 3개와 `users` 하나), 비밀번호 비교(SQL 비교와 BCrypt), 권한 규칙의 위치(DB 롤과 코드·테스트)다. 직접 구성한 이유와, 발주처 표준을 따라야 할 때 옮기는 순서는 [비교 문서](UAT_SEC_COMPARISON.md)에 있다. 원본에도 개인정보 조회 로그 AOP(`EgovPrivacyLogAspect`)가 있다. 11차의 명시적 기록과 무엇이 다른지도 같은 문서에 적었다.
