## SI 산출물

- [테이블 정의서](si/TABLE_DEFINITION.md), [ERD](si/ERD.md): `scripts/generate-db-docs.py` 가 실제 DB 에서 만든다.
- [화면 목록과 요구사항 추적표](si/SCREEN_LIST.md): 화면 27개, 요구사항 13개. 보안 설정과 테스트를 대조하며 직접 썼다.

테이블 정의서를 손으로 쓰면 마이그레이션이 늘 때마다 실제 스키마와 어긋난다. 그래서 설명은 DDL 의 COMMENT 에 두고, 문서는 `information_schema` 를 읽어 다시 만든다. 외래키 없이 값으로 이어진 관계는 ERD 에 점선으로 그리고, 외래키를 두지 않은 이유를 표로 남겼다.

요구사항 추적표의 시험 칸에는 실제 테스트 클래스 이름을 적었다. "이 요구사항은 무엇으로 확인했나"에 바로 답할 수 있게, 테스트가 없는 요구사항은 넣지 않았다.

## 동시성 테스트 두 개

공지 동시 첨부(8차에서 미룬 것). 담당자와 관리자가 같은 공지에 동시에 파일을 올리는 경우다. 앞 요청은 커밋을 미루고, 뒤 요청은 다른 스레드에서 게시물 행 잠금을 기다린다. 앞 요청이 커밋하면 뒤 요청은 같은 첨부 묶음에 다음 순번으로 붙는다. 잠금 SQL 에서 `FOR UPDATE` 를 빼면 이 테스트가 실패하는 것도 확인했다.

여기서 하나 배웠다. MySQL 기본 격리 수준(REPEATABLE READ)에서는 트랜잭션의 첫 조회 때 읽는 기준 시점이 정해진다. 잠그기 전에 일반 조회를 먼저 하면, 잠금을 얻은 뒤에도 예전 값을 읽는다. 그래서 잠금이 첫 문장이어야 한다.

동시 가입(9차에서 미룬 것). 같은 아이디나 사업자등록번호로 두 가입이 동시에 들어오면 둘 다 중복 확인을 통과할 수 있다. 이때 늦은 쪽은 DB 의 UNIQUE 에서 막히고, 서비스가 이 오류를 "방금 같은 정보로 가입한 계정이 있다"는 안내로 바꾼다.

두 테스트 모두 sleep 으로 순서를 짐작하지 않고, `performance_schema.data_lock_waits` 로 실제로 잠금을 기다리는지 확인한다. 이 부분은 `DatabaseLockWait` 로 묶어 동시성 테스트 세 개가 같이 쓴다.

## 공통컴포넌트 로그인·권한과 비교

공통컴포넌트의 로그인(uat)과 권한(sec)을 쓰지 않고 Spring Security 로 직접 구성한 이유, 발주처 표준을 따라야 할 때 옮기는 순서를 [비교 문서](UAT_SEC_COMPARISON.md)에 정리했다.
